## What it is
- A responsive website, installable as a PWA (added 17 Nov 2026), for salaried users in India. The user enters a monthly salary and pay day. The app splits each pay cycle into a 50/30/20 plan (needs / wants / savings+investments), the user logs expenses, and reports compare actual spending to the plan.
- Goals: a tool the owner uses daily AND a portfolio piece for SDE / full stack job applications. No deadline. Production-quality engineering matters more than feature count.
- No AI features. AI was deliberately dropped.
- Owner: Hemant, MCA student in Bengaluru. Primary stack is MERN, but this project is Java/Spring Boot + React on purpose (second backend showcase next to the Shortify project).

## Domain rules
- Money: BIGINT paise everywhere (1 rupee = 100 paise). The API only accepts and returns whole paise. UI shows rupees with 2 decimals in Indian format; convert text to paise by string handling, never floats. Salary limits: 100 to 1,000,000,000 paise (Rs 1 to Rs 1 crore). Expense limit: up to 10,000,000,000 paise.
- Pay cycle: runs from one pay date to the day before the next. If the pay day does not exist in a month (29-31), use the last day of that month. CycleCalculator: payDateInMonth, containing, startingOn, nextAfter. Pay day change (decided 10 Nov 2026): the current cycle AND the next full cycle keep the old pay day; the new pay day takes effect only after that, so the transition cycle comes one cycle later (needs a pending pay day stored, so a new migration). The transition cycle itself can still be short or long (even 1 day).
- STORED CYCLES BEAT THE FORMULA: always look dates up in the database first (findContaining); the formula is only used to create new cycles after the newest stored one.
- Budget split (BudgetSplit): needs = floor(income*needsPct/100), wants = floor(income*wantsPct/100), savings = remainder, so the three always equal the income. Income = salary + bonus of that cycle.
- Split presets (cycle/SplitPreset, owner's choice 19 Nov 2026; no free-form percentages): BALANCED 50/30/20 (default), HIGH_RENT 60/20/20, SAVER 50/20/30, LOW_COST 40/30/30. Chosen at onboarding (optional, default BALANCED) or in Settings; a change re-splits the current cycle and later cycles copy it; past cycles keep theirs.
- Bonus: one amount per cycle (0 = none), split with the same percentages as salary. It is NOT copied to the next cycle: roll-forward splits the newest cycle's salary only. A salary change keeps the bonus and the split.
- Opening balance: optional, asked at onboarding ("Do you already have savings?") and editable in Settings. It only adds to the Total savings figure on Reports (client side); it never changes a cycle's plan.
- Savings is derived: salary - needs spent - wants spent. "Invested" = sum of INVESTMENT expenses, a breakdown INSIDE savings, not subtracted from it. Unspent money counts as savings. Warn if logged spending exceeds salary. Overspend flags on needs and wants even when savings covers them. Negative savings is shown as a deficit, not zero.
- Savings overview (planned): sum of saved over completed cycles that have at least one expense, current cycle shown separately. Weekly view (planned): prorated per day from the cycle's daily rate, weeks start Monday, split across cycles. Yearly (planned): cycles grouped by the calendar year of their start.
- Default categories (13, seeded at onboarding): NEED: Rent, Groceries, Transport, Utilities and Bills, Health, EMI and Loans. WANT: Dining, Shopping, Entertainment, Subscriptions. INVESTMENT: Investments, Courses and Learning. Plus "Other" with NULL type (protected: cannot be renamed, retyped, archived or deleted).
- Expenses: type comes from the category; for Other the request MUST send type; for typed categories sending type is a 400. The expense keeps the type it was logged with even if the category is retyped later (editing with the same category keeps the stored type; changing category re-snapshots). Future dates blocked, dates before 2000-01-01 blocked, date defaults to today in Asia/Kolkata (injected Clock bean, app is India-only). No new expense in an archived category (editing an old one in place is allowed).
- Recurring expenses (decided 17 Nov 2026): monthly on a day of the month (29-31 fall on the last day of shorter months, MonthlySchedule recomputes from the chosen day each month). Nothing is logged automatically: when next_due_date <= today the dashboard asks; Confirm logs a normal expense through ExpenseService (all expense rules apply, amount editable, date defaults to the due date) and moves next_due_date one month; Skip moves it without logging. Missed months are asked one at a time, oldest first. Created rules start at the first occurrence on or after today. Changing the day keeps the waiting month; resuming after a pause skips months that passed while paused. Confirm/Skip carry the dueDate being answered and lock the row (SELECT FOR UPDATE), so double taps or two devices give 409 "This payment was already handled" instead of a duplicate expense. A category used by a recurring expense cannot be deleted (409); an archived category cannot be confirmed (409 "This category is archived"). Limit 50 per user. Managed only on the Recurring page (no switch on Add expense).
- Limits: 50 categories per user, 20,000 expenses per user. Another user's resource always returns 404 (never 403).

## Security decisions (keep them)
- Access token: HS256 JWT, 15 minutes, subject = user UUID, signed with JWT_SECRET (startup fails if missing or under 32 bytes). Stateless sessions, CSRF disabled (bearer tokens), BCrypt passwords (min 8 chars, max 72 bytes), email trimmed and lowercased.
- Refresh token: 32 random bytes (SecureRandom), base64url; only its SHA-256 hash is stored; 30 days; cookie refresh_token (HttpOnly, SameSite=Strict, Path=/api/auth, Secure from COOKIE_SECURE). Rotation is ONE atomic conditional UPDATE (revokeIfActive); presenting a revoked token again revokes all of that user's tokens (reuse detection). Grace (V13, 27 Nov 2026, branch feature/final-touches): a token replaced by rotation less than 2 minutes ago (RefreshTokenService.REUSE_GRACE) may be presented ONCE more and gets its own new token (rotateIfActive sets rotated_at; useGraceIfAllowed is one conditional UPDATE on grace_used), which covers a lost response and two tabs refreshing at once; a third use, a use after 2 minutes, or any use after revokeAllByUserId (which also sets grace_used) or after logout (closeGrace) is reuse. The frontend still never sends two refreshes at once in one tab.
- Login returns the same 401 for unknown email and wrong password (dummy hash for timing). Duplicate email returns a generic 409 (known trade-off: it reveals registered emails).
- Repositories extend the bare Spring Data Repository (not JpaRepository) so there is no findById without a user: every query takes userId. Use saveAndFlush/flush THROUGH the repository (not an injected EntityManager) so database errors become DataIntegrityViolationException and map to 409 instead of 500.
- Races are handled with atomic SQL (conditional UPDATE, ON CONFLICT DO NOTHING), not read-then-write in Java.
- Global handler: never echoes rejected values, never logs request bodies, tokens, passwords or SQL; conflict logging is only the exception class and SQLState. Fractional JSON numbers for integer fields are rejected (400 "Malformed request body"). Malformed UUID or parameter gives 400 via MethodArgumentTypeMismatchException. Do not use @Validated constraints on request parameters (they would fall into the catch-all and return 500); validate manually in services.

- Error monitoring (branch feature/sentry, 18 Nov 2026): backend config/SentryConfig starts the core Sentry SDK only when app.sentry.dsn (SENTRY_DSN) is set, sendDefaultPii false, no tracing, closed on shutdown; ApiExceptionHandler.handleAny (unexpected 500s) calls Sentry.captureException because the handler answers every error itself. Frontend monitoring.ts: only in production builds with VITE_SENTRY_DSN; the SDK is loaded on demand through sentryClient.ts (three named exports, ~31 kB gzip chunk; nothing when unset); dataCollection turns off user info, cookies, headers, bodies and query params; beforeSend/beforeBreadcrumb cut ?token= out of URLs (scrubUrl, unit-tested); setMonitoredUser tags the user id only (never the email). components/ErrorBoundary wraps the app: a crash shows "Something went wrong" with Reload instead of a blank page and is reported.
- Rate limiting (branch feature/rate-limiting, 16 Nov 2026): RateLimiter = in-memory Bucket4j buckets per (limit name, key), greedy refill, time from the injected Clock (tests move a MutableClock), max 50,000 keys (evicts full buckets, then fails closed with 429), @Scheduled eviction every 10 min (SchedulingConfig enables scheduling). AuthRateLimits: login per IP 20/15 min and per email 10/15 min (checked BEFORE the BCrypt check), register per IP 5/h and global 50/h; properties app.rate-limit.*. ClientIp = first X-Forwarded-For entry (Vercel sets it; spoofable when calling Render directly), else remote address. 429 + Retry-After + "Too many attempts. Please try again in N minutes."; logs only the limit name. Single-instance only; counts reset on restart. AbstractIntegrationTest sets the limits to 100000; RateLimitIntegrationTest uses small ones in its own context.

- Refresh-token cleanup (branch feature/token-cleanup, 16 Nov 2026): RefreshTokenCleanup deletes rows (revoked or not) whose expires_at is more than 7 days in the past, via one JPQL bulk delete. Revoked-but-unexpired rows are KEPT because reuse detection needs them. Runs 5 minutes after start and then every 6 hours (fixed delay), not at a time of day, because the Render free instance sleeps when idle. Logs only the count.

- Password reset (branch feature/password-reset, 17 Nov 2026): V5 password_reset_tokens (id, user_id fk cascade, token_hash unique, expires_at, used_at, created_at; RLS on). POST /api/auth/forgot-password {email} -> always 202, work done on a virtual-thread executor so timing does not reveal accounts; new link invalidates older ones; 30-minute expiry; only SHA-256 hashes stored (SecureTokens). POST /api/auth/reset-password {token, password} -> 204; consumeIfActive is one conditional UPDATE; then new BCrypt hash, other links invalidated, all refresh tokens revoked; invalid -> 400 "This reset link is invalid or has expired. Request a new one." Rate limits app.rate-limit.password-reset-per-ip 10/h and per-email 3/h. Email: mail package, EmailSender interface, BrevoEmailSender (JDK HttpClient to https://api.brevo.com/v3/smtp/email, header api-key) because Render free blocks SMTP; logs only status codes, never recipients or links. Expired links deleted by a scheduled job a day after expiry. PasswordResetIntegrationTest (6 tests) replaces the sender with a capturing one.

## Code conventions
- Feature packages; records for DTOs; entities have protected no-arg constructor, getters and minimal mutators, user_id and category_id as plain UUID columns (no relationships), created_at insertable=false/updatable=false, enums as EnumType.STRING.
- Services hold the business rules and use @Transactional on every method that changes data (including derived deletes). Controllers read the user id from the JWT subject (@AuthenticationPrincipal Jwt).
- Short comments that explain WHY, not what.
